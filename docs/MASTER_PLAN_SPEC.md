# マスタープランの指示（ユーザー提供の原文。Phase 0〜11・共通条件）

横浜みなと釣り旅 — 関東全域3D化・ゲーム全面進化プロジェクト

最重要命令：自律実装・連続実行

あなたは本プロジェクトの主任ゲームエンジニア、3Dグラフィックスエンジニア、ゲームデザイナーとして、既存ゲーム「横浜みなと釣り旅」の大規模改修を担当してください。

対象リポジトリ：
https://github.com/kentokento469/yokohama-fishing

公開先：
https://kentokento469.github.io/yokohama-fishing/

この依頼は計画書作成ではなく、実際のゲームを改修する実装依頼です。

以下のPhase 0〜Phase 11を、指定された順序で進めてください。

自律実行ルール

* 各Phaseについて、実装・テスト・修正・進捗保存まで行う。
* 1つのPhaseが完了したら、ユーザーの追加指示を待たずに次へ進む。
* 実装できる範囲で自主的に技術選定する。
* 不要な質問や途中確認を行わない。
* 小さなエラーは自己解析して修正する。
* 外部データ取得に失敗した場合は別の取得経路を試す。
* 不可能な項目は記録し、可能な部分を進める。
* ただし完了必須条件が満たせないPhaseを、成功扱いして次に進めない。
* 全Phaseが終わるまで、自分の判断で作業を終了しない。
* 実行環境や利用制限による停止は許容し、再開可能な状態を残す。
* 不要な長文報告やコード全文の出力を避ける。
* 既存機能の破壊を禁止する。
* 外部APIへの有料契約、実際の課金、破壊的操作、権限回避は行わない。
* 必要な承認が得られない場合は、その操作を保留して安全に継続する。

Phase 0：現状分析・保全・作業管理

最初に現在のリポジトリを解析する。

1. CLAUDE.mdを読む。
2. index.htmlを含む全ソースコードを確認する。
3. 既存の釣りシステム、魚種、釣り場、マップ、NPC、セーブデータを調査する。
4. 既存機能と依存関係を一覧化する。
5. 既存コードをGitで保全し、作業用ブランチを作成する。
6. 必要に応じてHTML・CSS・JavaScriptをモジュール分割する。
7. GitHub Pagesとの互換性を維持する。
8. テストとビルド確認を自動化する。

セーブデータの既存キー hama-tsuri-v2 を確認し、保存データの移行機能を準備する。

docs/MASTER_PROGRESS.mdを作成し、各Phaseの進捗を記録する。

各Phaseは以下の状態で管理する。

* TODO：未着手
* ACTIVE：作業中
* DONE：動作検証まで完了
* BLOCKED：外部要因で完了できない

完了したPhaseにはGitコミットを作成する。

セッション開始時には進捗ファイルを確認し、完了済みの工程を繰り返さず、未完了箇所から継続する。

Phase 1：関東全域の実地理データ取得

対象地域

神奈川県・東京都・千葉県・埼玉県・茨城県・栃木県・群馬県。

現在ゲームに存在する全エリアを維持し、将来的に関東全域を探索可能にする。

横浜から鎌倉、逗子、葉山、横須賀、三浦、藤沢、茅ヶ崎、平塚、大磯、小田原、真鶴、湯河原などの海岸を含む。

千葉・茨城の海岸、東京湾、河川、湖、山間部にも対応する。

東京都島しょ部についても対応可能なデータ構造とし、取得範囲を記録する。

使用データ

GSI：国土地理院

DEM等の標高データを取得する。

実際の標高値を使用し、地形の高さを正確に再現する。

利用可能なデータの解像度を調査し、地域ごとに最良のデータを採用する。

PLATEAU

関東各都市の3D都市モデルを取得する。

利用可能なLOD1・LOD2等の建物モデルを使用する。

未整備地域ではOpenStreetMapの建物輪郭と高さ情報から3D建物を生成する。

OpenStreetMap

道路、歩道、建物、海岸線、港湾施設、砂浜、河川、湖、鉄道、橋、森林、公園、桟橋、防波堤などを取得する。

既存の関東地方OSMデータが利用できる場合は再利用する。

取得できない場合

Claude Codeから直接取得できない場合、次の方法を順に試す。

1. 公式配信URLから取得
2. 別の公式配信形式を利用
3. GitHub Actionsで取得
4. Pythonによる取得・変換処理
5. 事前配置したデータのインポート

外部アクセス制限が原因なら、取得処理をClaude Codeの実行環境から分離する。

取得済みデータはキャッシュし、再ダウンロードを抑制する。

大量のデータを無制限に取得しない。利用条件やアクセス制限を遵守する。

地域別・データ種別の取得成功率と欠損範囲を記録する。

Phase 2：関東全域の本格3D地形化

現在のThree.jsを基盤に、実際の地理情報から3D地形を生成する。

必須機能

* 標高に基づいた地面の立体化
* 坂道、斜面、崖、山、谷の再現
* 海岸線の正確な形状
* 砂浜と岩場の違い
* 河川敷と護岸の高さ
* 桟橋・防波堤・港湾施設
* 建物の実際の配置と高さ
* 道路と地形の高さの整合
* プレイヤーと地形の衝突判定
* 建物や地面を貫通しない移動

既存のSC=3による距離圧縮と実地理座標を分離する。

詳細な探索エリアでは原則として1:1の実寸表示を目指し、広域移動やマップ表示には別の縮尺を使用できるようにする。

すべての地域を同時にロードしない。

地形はチャンク方式で管理し、周辺地域を読み込み、遠方はLODで簡略化する。

座標精度、チャンク境界、テクスチャ境界を修正する。

既存の徒歩移動・バス移動を残す。

広域マップから関東各地に移動できるようにする。ただし、全地点間の連続移動が技術的に難しい場合は地域ロード方式を使用する。

全関東の地形データを処理できる共通エンジンを先に完成させ、その後地域データを順次適用する。

実データがない場所を架空の地形で補完した場合は、必ず実測データとの違いを管理する。

このPhaseの完了条件：
対象全域の地形を共通エンジンで表示可能で、実測標高の適用範囲と不足地域を確認できること。

一部地域だけの3D化で全域完了と判定しない。

Phase 4：NPCと街の生活感

ゲーム世界が無人の模型に見えないようにする。

歩行者、釣り人、地元住民、観光客、自転車利用者、車両、船舶などを配置する。

自然な移動・待機・会話・行動アニメーションを実装する。

地域の環境に応じたNPCを出現させる。

釣り禁止エリアでは、警告表示に加え、地元住民や管理者から注意される演出も追加する。

NPCの会話には地域性や個性を持たせる。注意の仕方が厳しい住民なども登場させ、現実の生活感を演出する。

ただし、実在人物を無断で再現しない。

釣り禁止・立入禁止の判定は、確認できる現地ルールに基づくこと。情報不足の地点を無条件で釣り可能にしない。

適法に釣りができる砂浜、海釣り施設、河川、湖なども地域拡張の対象とする。

NPCは必要な範囲のみ読み込み、スマホ性能に合わせて出現数を調整する。

Phase 5：カメラ操作の改善

現在のカメラの上下角度制限を修正する。

現状のpitch制限を調査し、上方向にも自然に視点移動できるようにする。

必須要件

* 水平から約80度上まで見上げられる
* 下方向にも自然に視点移動できる
* カメラが地面や建物に貫通しない
* 高層ビルや山を見上げられる
* 釣り中も必要な範囲で視点を動かせる
* カメラの回転感度を調整できる
* 左側の移動ジョイスティックに干渉しない
* 必要なら一人称視点と三人称視点を切り替え可能にする

カメラ角度を変えても既存の釣り操作が壊れないようにする。

Phase 6：釣りの3D表現とUI刷新

絶対条件

現在のテンションゲージによるファイトシステムは維持する。

「長押しで巻く」「テンションが危険域に達したら離す」という操作感を変えない。

キャスト、リトリーブ、しゃくり、合わせなどの既存操作も可能な限り維持する。

改善するのは主に見た目、アニメーション、情報表示、操作時の視認性。

釣り竿・リール

* 実際の釣り竿に近い3Dモデル
* ロッドのしなり
* リールの回転
* スプールの動き
* ラインの張力表現
* ドラグによる糸の放出
* ロッドアクションとルアーの連動
* アタリに応じた竿先の動き

竿・リール・ラインの性能と実際の挙動を連動させる。

ゲージ表示

テンションゲージのロジックは維持する。

テンションの増減を竿の曲がり、ラインの状態、リール音と連動させる。

危険域では視覚・音で知らせる。

テンションゲージの位置は操作中の指に隠れない場所へ変更する。

キャスト

キャスト方向、飛距離、着水位置を自然に表示する。

キャスト先の水面の輪と説明文字を重ねない。

竿からラインが放出されるアニメーションを改善する。

釣りUI

スマホ向けの高品質なUIに変更する。

* 操作部分と情報部分を分離
* 半透明で控えめなHUD
* 必要な情報だけ表示
* 使用していないUIは自動的に薄くする
* テンション・巻き速度・飛距離・水深を整理
* 画面端のセーフエリアを確保
* iPhone縦画面に最適化
* 指で隠れる表示を削減
* マップ・ショップ・図鑑のデザイン統一

UIの操作方法を大きく変更しないこと。

Phase 7：魚の写真と3Dモデルを全面刷新

現在の魚の簡易イラストを、高品質な魚種別ビジュアルに置き換える。

写真

ゲーム内に登録されている魚種を全件抽出する。

魚種ごとに実物の写真を用意する。

* 正確な魚種
* 和名・学名の一致
* 高解像度
* 正しい体型・色・模様
* 適切なライセンス
* 撮影者・出典の記録

Wikimedia Commons、iNaturalistなど利用可能なソースを検討する。

ダウンロード時には再配布や改変の条件を確認する。

利用条件が不明な写真や権利上使えない画像は採用しない。

画像のない魚種を別の魚の写真で代用しない。

釣果画面、魚図鑑、記録画面に写真を使用する。

3Dモデル

魚種ごとに、体型・鰭・鱗・模様を反映した3Dモデルを導入する。

可能な限り実在魚種に近い形状を使用する。

魚の大きさは釣果の体長に連動させる。

釣り上げた魚の暴れ方、尾鰭の動き、着地時の動作を改善する。

釣果写真と3Dモデルは別々に管理する。

魚種拡張

関東の海水魚・汽水魚・淡水魚を含め、魚種データを増やす。

それぞれに生息域、季節、時間帯、水深、餌、サイズ、重量などを設定する。

既存魚種を削除しない。

Phase 8：釣具・装備システムの高度化

ロッド、リール、ライン、ルアー、ジグ、ワーム、針、仕掛けなどのグラフィックを改善する。

実際の釣具のような性能差を設定する。

価格・種類

将来的にカテゴリーごとに100種類規模へ拡張できるデータ構造にする。

実在メーカーの商品デザインやロゴの無断流用を避け、オリジナル商品名・デザインを基本とする。

ゲーム内通貨による購入を中心にする。

Phase 10：生き餌・泳がせ釣り

釣った魚を餌として使用できるシステムを実装する。

アジ、イワシなど適切な小魚を生き餌として管理する。

生け簀、活かしバケツ、エアポンプなどを追加する。

生き餌の状態を管理する。

* 魚種
* サイズ
* 生存状態
* 経過時間
* 水温・酸素条件
* 対象魚との相性

泳がせ釣りで大型魚を狙えるようにする。

生き餌の種類、投入水深、泳ぎ、仕掛けによって釣果が変化する。

魚を釣る→餌として保管→大型魚を狙う、という循環を実装する。

地域の釣りルールに応じ、使えない餌や仕掛けを制限できる構造にする。

Phase 11：市場・魚売却・ゲーム経済

現在の即時換金方式を発展させる。

釣った魚をクーラーボックスに保管し、市場で売却するシステムを追加する。

魚の保管

* 魚種
* 重量
* サイズ
* 鮮度
* 保存時間
* 保存方法
* 生存状態

市場

地域ごとに市場や買い取り施設を配置する。

魚種、重量、サイズ、鮮度、季節、需要に基づいて買い取り価格を計算する。

市場ごとに価格差を設定する。

適切に保管した魚は高く売れるようにする。

ゲーム内の価格・取引はフィクションとして扱い、実際の漁獲物販売の法的許可を再現していると誤認させない。

釣果の使い道

釣った魚には次の選択肢を用意する。

1. 持ち帰って市場で売る
2. 魚拓として記録する
3. 生き餌として使用する
4. リリースする
5. その他の保存・利用方法は将来拡張可能にする

魚拓の記録は魚の所有状態とは独立して保存する。

毒魚や保護対象魚などの取り扱いも適切に管理する。

売却収入を釣具、装備、移動費などに利用できるようにする。

ゲーム内経済には多少の理不尽さや風刺的な要素を持たせてもよいが、実際の課金システムや外部決済は導入しない。

完了判定と品質管理

各Phaseについて以下を必須とする。

1. 実際のコード変更
2. エラー・構文チェック
3. 必要なテスト
4. ゲーム起動確認
5. 既存機能の回帰テスト
6. モバイル画面サイズでの確認

実装が不完全ならDONEにしない。

全域3D化が未完了の場合、魚拓など後続Phaseを先に完成させて全体完了と報告しない。

ただし他Phaseの独立した基盤準備やテスト作成は進めてよい。

トークンと長時間作業の管理

トークン消費を抑える。

* 不要なコード全文の出力禁止
* 同じソースの繰り返し読込を削減
* 大量データを会話に出力しない
* スクリプトで機械的に処理できる作業は自動化
* 地理データは一括ではなく地域単位で処理
* 必要なら専門サブエージェントを活用
* 定期的に進捗ファイルを更新
